# Launchlane

دستیار استقرار و بررسی سلامت سرویس، با پیشنهاد مبتنی بر شواهد و تأیید شما پیش از اقدام حساس.

**وضعیت فعلی:** پروژه محلی را با انتخاب‌گر پوشه معرفی کنید یا مخزن و شاخه GitHub را انتخاب کنید. Launchlane فایل‌ها را بدون اجرای کد بررسی و بسته خصوصی آماده می‌کند. اتصال لیارا، پیشنهاد و تأیید پایدار، انتشار روی یک برنامه Node موجود و گزارش مشکل سایت پیاده شده‌اند. یک چرخه کنترل‌شده واقعی، خطای ۵۰۰، تشخیص مبتنی بر شواهد و انتشار کد اصلاح‌شده را گذرانده است؛ [گزارش آزمون زنده](docs/evidence/controlled-live-cycle.md) محدوده دقیق را نشان می‌دهد. راه‌اندازی دوباره با تأیید و بررسی همان صفحه قرارداد آزموده‌شده دارد، اما اجرای زنده و پایان restart تأیید نشده‌اند. ورود واقعی GitHub، پیشنهاد قیمت و تغییر متغیرهای محیطی نیز باز هستند.

## اجرای محلی

Node 24.15+ از شاخه 24.x و npm لازم است. برای مسیر آفلاین کلید Liara/مدل لازم نیست.

```text
npm ci
npm run setup:local
npm run dev
```

صفحه پیش‌فرض: `http://127.0.0.1:3000`. کلید ورود را از `.local/operator-access.txt` به‌صورت محلی بردارید؛ این فایل و `.env.local` خصوصی‌اند و وارد Git نمی‌شوند. setup مقدار موجود credentialها را حفظ می‌کند. پس از تغییر config یا کد persistence/migration، server را در زمانی که عملیات زنده‌ای در حال اجرا نیست restart کنید؛ اتصال SQLite در توسعه بین reloadها حفظ می‌شود و نوسازی مرورگر جای restart فرایند را نمی‌گیرد. برای اجرای production:

```text
npm run build
npm start
```

در terminal جدا، در حالی که server اجراست:

```text
npm run lint
npm run typecheck
npm run test:domain
npm test
```

`npm test` دو smoke اجرای server است. `test:domain` policy، persistence، source و قرارداد transport/خطا را می‌سنجد. برای پورت دیگر، `LAUNCHLANE_ORIGIN` و پورت اجرا را با هم عوض کنید و برای smoke، `TEST_BASE_URL` را نیز تنظیم کنید.

برای HTTP و UI، پس از build و بدون نیاز به اجرای server جداگانه:

```text
npm run test:http
npx playwright install chromium
npm run test:browser
```

این دو دستور server تولیدی موقت با محدوده مصنوعی و کلیدهای provider خالی ایجاد می‌کنند. آزمون مرورگر ۹ عرض از ۲۸۰ تا ۱۲۸۰ پیکسل، انتخاب/بازیابی پروژه، اتصال حساب‌ها با پاسخ کنترل‌شده، approve/reject، خطا، لغو، کیبورد، متن ۲۰۰٪ و axe را می‌سنجد؛ تصاویر و گزارش در `.artifacts/` محلی می‌مانند. داده حساب و نتایج provider در تست مصنوعی‌اند؛ نتیجه شاهد اتصال حساب واقعی، deploy یا کیفیت مدل نیست.

## استفاده از میز کار

1. وارد شوید و «انتخاب پوشه پروژه» یا «انتخاب از GitHub» را بزنید. نمونه فقط با «امتحان با پروژه نمونه» انتخاب می‌شود. انتخاب‌گر محلی پوشه‌های مجاز سرور همین رایانه را می‌خواند؛ upload پوشه دستگاه مرورگر نیست. محدوده آن با `LAUNCHLANE_WORKSPACE_ROOT` تنظیم می‌شود؛ کل دیسک مجاز نمی‌شود.
2. فایل‌ها خودکار و بدون اجرای script بررسی و بسته خصوصی آماده می‌شود. نام/حجم فایل‌ها قابل بازبینی است؛ مرحله دستی بسته‌سازی یا واردکردن دوباره پورت تشخیص‌داده‌شده ندارید. پروژه ناقص یا پورت نامعلوم سؤال مشخص ایجاد می‌کند.
3. از «حساب‌ها»، لیارا را متصل کنید. کلید به‌جای صرف ذخیره‌شدن، با سه GET محدود برای هویت، تیم ثابت و برنامه‌ها بررسی می‌شود. تیم مجاز را مسئول نصب در `LIARA_TEAM_ID` تعیین می‌کند؛ کاربر نام برنامه را از فهرست انتخاب می‌کند. allowlist مدیر، اگر تنظیم شده باشد، محدودیت بالادست است. اتصال فقط یک app انتخابی را مجاز می‌کند و مجوز تغییر همه برنامه‌ها نیست.
4. پیشنهاد شامل مقصد، نسخه اجرای Node، فایل‌های همان نسخه، اثر و وضعیت نامشخص هزینه است. تأیید به همین ورودی‌ها و revision GitHub متصل می‌شود؛ انتخاب تازه یا تغییر فایل‌ها تأیید قبلی را باطل می‌کند. انتشار تازه از پیشنهاد v5 استفاده می‌کند؛ v1/v2/v3/v4 برای اجرای تازه به پیشنهاد جدید نیاز دارند و نتیجه انتشار تاریخی v4 قابل بازخوانی است.
5. نتیجه با نوسازی و Back/Forward بازیابی و تازگی فایل‌ها بررسی می‌شود. بازیابی تأیید منقضی را تمدید نمی‌کند. ثبت تأیید، شروع انتشار و تأیید پاسخ سایت سه وضعیت جدا هستند.

برای ورود GitHub روی Windows x64، مسئول نصب یک‌بار `npm run setup:github` را اجرا کند. نسخه رسمی 2.103.0 با checksum بررسی و فقط در ابزارهای محلی نصب می‌شود؛ PATH یا ورود سراسری تغییر نمی‌کند. ورود از device flow ابزار رسمی و با grant انسان انجام می‌شود؛ credential باید در keyring باشد. مجوزهای گسترده CLI پیش از ورود توضیح داده می‌شوند؛ برای محصول عمومی GitHub App می‌تواند محدودتر باشد. [دلیل انتخاب روش](docs/decisions/0001-account-connections.md) و محدودیت‌ها ثبت شده‌اند.

برای «بررسی مشکل سایت»، برنامه متصل و نشانه مشکل را انتخاب کنید. نشانی عمومی امن سایت را می‌توان در حساب‌ها ثبت کرد؛ این کار دامنه لیارا را تغییر نمی‌دهد. پس از فعال‌شدن مجاز خواندن، اطلاعات همان برنامه و صفحه جمع‌آوری می‌شود؛ توضیح خودکار علت یک اقدام جدا و وابسته به آماده‌بودن مدل است. بررسی دوباره فقط پاسخ همان صفحه را می‌خواند و هیچ اصلاحی اجرا نمی‌کند. گزارش ابتدا مشکل، علت احتمالی، اقدام و نتیجه تازه را نشان می‌دهد؛ شواهد اولیه و تازه قابل بازکردن‌اند. داده ناکافی، علت قطعی تولید نمی‌کند.

«امتحان با نمونه اختلال» اختیاری و در تمام گزارش مشخص است؛ داده و تحلیل آن simulated/scripted هستند و هیچ تماس مدل/حساب ندارند. تغییر نامرتبط، 500 را حفظ می‌کند. نتیجه عادی و نمونه در SQLite متعلق به همان کاربر نگهداری و پس از جابه‌جایی، نوسازی یا ورود مجدد بازیابی می‌شوند؛ مرورگر فقط شناسه غیرحساس در URL دارد. تحلیل در حال اجرا با نوسازی تکرار نمی‌شود و پس از قطع فرایند، ناموفق و بدون بازپخش خودکار بازیابی می‌شود.

در نتیجه بررسی، «گزارش برای اصلاح کد» یک فایل Markdown برای برنامه‌نویس یا Coding Agent آماده می‌کند: روش تکرار همان صفحه، شواهد زمان‌دار، فرضیه‌های ارجاع‌دار، محدوده اصلاح و معیار بررسی. پیش‌نمایش و دریافت محلی‌اند؛ فایل به editor یا مدل دیگری ارسال نمی‌شود و مجوز تغییر نیست. کد پروژه، هویت حساب، details خام اضافی و credentialهای شناخته‌شده ضمیمه نمی‌شوند؛ اطلاعات خصوصی کسب‌وکار و الگوهای ناشناخته را پیش از اشتراک بازبینی کنید. آخرین مشاهده همان صفحه و نامعلوم‌ماندن پاسخ restart جدا ثبت می‌شوند. نام فایل/خط/دستور مخزن حدس زده نمی‌شود. داده مصنوعی با route/SQLite واقعی محلی و بازپخش آفلاین incident واقعی ذخیره‌شده 500→200 سنجیده شده‌اند؛ استفاده مستقل یک reader تازه هنوز تأیید نشده است.

`.env.example` با config مصرف‌شده هماهنگ است. هر سه gate `LAUNCHLANE_ENABLE_MUTATIONS`، `LAUNCHLANE_ENABLE_LIVE_MODEL` و `LAUNCHLANE_ENABLE_LIVE_LIARA` پیش‌فرض false هستند. فعال‌کردن mutation به‌تنهایی approval ایجاد نمی‌کند؛ انتشار به live-Liara، اتصال/app مجاز، origin و پیشنهاد v5 تازه نیاز دارد؛ راه‌اندازی دوباره از پیشنهاد مستقل v6 استفاده می‌کند. رمز پنل Liara توکن PaaS نیست؛ کلید مدل فقط به میزبان ثابت BoxAPI مجاز است. probe واقعی به نشانی HTTPS مجاز همان برنامه در حساب‌ها یا `LAUNCHLANE_PROBE_ORIGINS` نیاز دارد؛ تنظیم مدیر مقدم است، redirect و IP خصوصی رد می‌شوند. تا تطبیق حساب و مجوز scope/budget، این gateها خاموش بمانند.

انتشار روی **برنامه Node موجود** در آزمون واقعی بررسی شده است. مسیر هدف باید JSON کوچکی مانند `{"revision":"my-v2"}` برگرداند. پیشنهاد تازه v5 شناسه داخلی برنامه، پلن، نسخه اصلی Node، بسته و معیار status/path/revision را به تأیید متصل می‌کند. انتشار، پلن یا متغیرهای محیطی را تغییر نمی‌دهد و هزینه در پیشنهاد همچنان نامشخص است. رسید بسته پیش از درخواست نسخه ذخیره می‌شود؛ پاسخ گم‌شده باعث ارسال خودکار دوباره نمی‌شود. آزمون زنده ثبت‌شده مربوط به v4 پیشین است؛ فیلد نسخه صریح v5 هنوز در حساب واقعی آزموده نشده است.

در «بررسی مشکل سایت»، راه‌اندازی دوباره یک اقدام اختیاری پس از مشاهده خطای تازه همان صفحه است. پیشنهاد، حساب و برنامه، نسخه فعلی، اثر وقفه و هزینه نامشخص را نشان می‌دهد. تأیید و اجرا جدا هستند؛ پس از پذیرش درخواست، پاسخ همان صفحه با همان نسخه دوباره خوانده می‌شود. این بررسی به پاسخ HTTP محدود است و پایان restart، رفع علت، محتوای صحیح یا بهبود سرعت را اثبات نمی‌کند. پاسخ گم‌شده، حتی با صفحه پاسخ‌گو، اجازه ارسال مجدد نمی‌دهد. نتیجه و شواهد پس از reload بازیابی می‌شوند؛ جزئیات محدودیت در [تصمیم restart](docs/decisions/0003-restart-acceptance.md) است. این مسیر با transport مصنوعی آزموده شده است؛ آزمون زنده restart هنوز انجام نشده.

با اعتبار، مدل و سقف مصرف مشخص، smoke صریح زیر حداکثر دو درخواست واقعی به BoxAPI می‌فرستد. این فرمان در checkها اجرا نمی‌شود و gate ذخیره‌شده را تغییر نمی‌دهد:

```text
npm run smoke:model -- --live
```

برای `gpt-6-luna` در مسیر Chat Completions، `MODEL_REASONING_EFFORT=none` برای ابزارخوانی لازم بود؛ بدون آن سرویس 400 داد. مدل‌های دیگر این نصب هنوز تست نشده‌اند. فهرست مدل‌های Chat مجاز در server enforce می‌شود؛ نه endpoint/provider پنهان داریم و نه fallback خودکار.

اگر build هنوز ادامه دارد، فقط نتیجه را دوباره بخوانید. پس از پاسخ ناموفق نیز «بررسی دوباره پاسخ و نسخه سایت» همان رسید را بدون انتشار دوباره بررسی می‌کند. READY، پاسخ liveness یا نسخه قبلی موفقیت محسوب نمی‌شود. توقف پیش از `release_started`، پس از بازخوانی، از release با رسید گم‌شده جدا می‌شود؛ پیشنهاد تازه همچنان تأیید تازه می‌خواهد. برای انتشار کد اصلاح‌شده، فایل‌ها را تغییر و پروژه را دوباره بررسی کنید.

## محدوده و دسترسی

MVP یک operator و یک scope مجاز دارد. privileged read/write به session، Host/Origin و در درخواست تغییر، CSRF وابسته‌اند؛ loopback جای authentication نیست. SQLite برای یک process است و approval/attempt به حافظه fallback نمی‌کنند. پاسخ گم‌شده یا قطع process، action را uncertain و write متعارض app را مسدود می‌کند.

بسته‌ها در `.data/source-artifacts/` یا زیر `LAUNCHLANE_STATE_DIR` خصوصی نگهداری می‌شوند؛ سقف هر بسته ۲۴ MiB، کل نگهداری ۱۲۸ MiB و ۳۲ فایل است. پاک‌سازی خودکار فعلاً وجود ندارد. حذف بسته متعلق به approval فعال، آن را قابل اجرا نمی‌کند؛ نگهداری/پاک‌سازی فقط پس از تعیین تکلیف اقدام‌ها انجام شود. پیشنهادهای قدیمی v1 خوانده می‌شوند ولی برای deploy به بسته متصل نیستند و باید دوباره ساخته شوند.

تشخیص فایل‌ها محدود و بدون اجرای کد است. در پروژه چندبخشی، پوشه همان برنامه را انتخاب کنید. نسخه Node از `engines.node` و `liara.json:node.version` انتخاب و در پیشنهاد نمایش داده می‌شود؛ تعارض، مقدار نامعتبر یا نبود شاخه سازگار، پیشنهاد اجرایی را می‌بندد. بدون تعیین نسخه، پیش‌فرض مستند 22 انتخاب می‌شود؛ نسخه Node رایانه مبنا نیست. انتخاب شاخه اصلی، نسخه جزئی محیط اجرا را تضمین نمی‌کند؛ این محدودیت کنار پیشنهاد دیده می‌شود. سناریوی زنده ثبت‌شده فقط Node 22 بود. حفظ دو متغیر پیش‌فرض در انتشار بعدی بررسی شد؛ حفظ secretها یا انواع دیگر تنظیمات از آن نتیجه نمی‌شود. مشاهده به صفحه اول حداکثر 50 release و JSON revision محدود است. rollback، reconcile حدسی رسید گم‌شده، چند process، میزبانی عمومی Launchlane و پایش دائمی پیاده نشده‌اند.

قابلیت پیاده‌نشده و بررسی زنده انجام‌نشده در گزارش وضعیت محصول صریح ثبت می‌شوند.
