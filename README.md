# Launchlane

دستیار استقرار و بررسی سلامت سرویس، با پیشنهاد مبتنی بر شواهد و تأیید شما پیش از اقدام حساس.

**مسیر اصلی:** پس از ورود، تب «انتشار پروژه» باز می‌شود. پروژه را از پوشه همین رایانه یا GitHub انتخاب و بررسی و آماده‌سازی را با دکمه شروع کنید؛ نوشتن پیام لازم نیست. مقصد، تغییر و هزینه پیش از اجرا برای تصمیم شما نمایش داده می‌شوند. اصلاح Node22 با آزمون مستقیم موجود در نسخه جدا و container محدود انجام می‌شود و انتشار به همان artifact آزموده‌شده نیاز دارد. چت فقط پنل اختیاری پایین چپ و سؤال‌های آن فقط‌خواندنی‌اند. ناوبری اصلی دو تب دارد و لینک قدیمی view=agent به انتشار می‌رسد. [شواهد انتشار هدایت‌شده](docs/evidence/guided-publication.md) دو چرخه محدود واقعی و مرزهای باز dependency/build، env و پذیرش عمومی را جدا می‌کند.

مسیر مستقل «بررسی مشکل سایت» نیز حفظ شده است: جمع‌آوری اطلاعات همان سایت و سپس «توضیح علت با هوش مصنوعی». نمونه‌ها از پیش تعریف شده‌اند و مدل واقعی نیستند. خاموش‌بودن قابلیت در همان صفحه توضیح داده می‌شود.

اگر پس از تغییر کد، پیام «نسخه سرور یا محل ذخیره‌سازی تغییر کرده است» دیدید، پس از پایان عملیات جاری سرور محلی را متوقف و دوباره اجرا کنید. نوسازی مرورگر، cache فرایند توسعه را بازسازی نمی‌کند. پایگاه داده را حذف نکنید؛ startup migrationهای جدید را با حفظ تاریخچه اعمال می‌کند.

پس از بررسی پروژه، بخش اختیاری «دامنه دلخواه وصل کنید» مسیر ثبت دامنه در برنامه، تنظیم DNS و فعال‌کردن گواهی را با لینک مستندات رسمی نشان می‌دهد. می‌توانید سرویس فعلی دامنه را نگه دارید یا راهنمای DNS لیارا را بخوانید. این قابلیت راهنماست؛ DNS یا گواهی را اجرا/تأیید نمی‌کند و مقادیر رکورد را از نام برنامه حدس نمی‌زند. بدون حساب هم راهنمای عمومی در دسترس است؛ مقصد مشخص از حساب و برنامه انتخاب‌شده می‌آید.

**وضعیت فعلی:** پروژه محلی را با انتخاب‌گر پوشه معرفی کنید یا مخزن و شاخه GitHub را انتخاب کنید. Launchlane فایل‌ها را بدون اجرای کد بررسی و بسته خصوصی آماده می‌کند. اتصال لیارا، catalog/قیمت پایه واقعی، ساخت مقصد Node در شبکه موجود، پیشنهاد و تأیید پایدار، انتشار و گزارش مشکل سایت پیاده شده‌اند. چرخه‌های کنترل‌شده واقعی، خطای۵۰۰، تشخیص، اصلاح کد و انتشار همان بسته آزموده‌شده را سنجیده‌اند؛ [گزارش‌های اعتبارسنجی](docs/verification.md) مرز هر شاهد را مشخص می‌کنند. یک درخواست restart نیز پذیرفته شد، اما خطای همان صفحه باقی ماند و رفع مشکل اعلام نشد؛ پایان restart همچنان تأیید نشده است. ورود واقعی GitHub، تغییر متغیرهای محیطی، ساخت شبکه و اجرای build/dependency عمومی هنوز بازند.

## اجرای محلی

این بخش برای نصب خصوصی اپراتور است. بازدیدکنندهٔ سایت عمومی نباید کلید محلی یا setup اجرا کند: مسیر جدید [ورود با حساب لیارا و تنظیم میزبانی](docs/hosted-access.md)، با `LAUNCHLANE_AUTH_MODE=liara` و origin HTTPS، فرم ایمیل/رمز و در صورت نیاز TOTP دارد. آماده‌بودن عمومی هنوز به ورود و انتشار زنده از میزبان واقعی، scope حساب شخصی و sandbox همان مقصد وابسته است؛ [شاهد و حدود](docs/evidence/liara-identity-login.md). `npm run test:login` مرورگر واقعی با دو هویت و provider کنترل‌شده را مستقل می‌سنجد.

برش npm قفل‌شده در Node22 اکنون تصمیم، نصب آفلاین در container، build/start موجود و همان معیار پاسخ را به worker مشترک وصل می‌کند؛ [ADR0012](docs/decisions/0012-locked-project-build.md). آزمون مستقل آن `npm run test:build-sandbox` است و Docker/image تثبیت‌شده لازم دارد. برای استفاده از cache محتوایی معتبر npm در همین آزمون، `LAUNCHLANE_TEST_NPM_CACHE` را به cache نصب معرفی کنید؛ هر فایل پیش از استفاده با integrity lockfile تطبیق داده می‌شود. cache credential یا کل home به container نمی‌رود. مسیر پیش‌فرض، tarball عمومی npm را می‌خواند. شاهد این برش Node22 است؛ build واقعی Next و env هنوز پذیرش ندارند.

Node 24.15+ از شاخه 24.x و npm لازم است. برای مسیر آفلاین کلید Liara/مدل لازم نیست.

```text
npm ci
npm run setup:local
npm run dev
```

صفحه پیش‌فرض: `http://127.0.0.1:3000`. کلید ورود را از `.local/operator-access.txt` به‌صورت محلی بردارید؛ این فایل و `.env.local` خصوصی‌اند و وارد Git نمی‌شوند. setup مقدار موجود credentialها را حفظ می‌کند. پس از تغییر config یا کد persistence/migration، server را در زمانی که عملیات زنده‌ای در حال اجرا نیست restart کنید؛ اتصال SQLite در توسعه بین reloadها حفظ می‌شود و نوسازی مرورگر جای restart فرایند را نمی‌گیرد. برای اجرای production:

```text
npm run build
npm start
```

در terminal جدا، در حالی که server اجراست:

```text
npm run lint
npm run typecheck
npm run test:domain
npm test
```

`npm test` دو smoke اجرای server است. `test:domain` policy، persistence، source و قرارداد transport/خطا را می‌سنجد. برای پورت دیگر، `LAUNCHLANE_ORIGIN` و پورت اجرا را با هم عوض کنید و برای smoke، `TEST_BASE_URL` را نیز تنظیم کنید.

برای HTTP و UI، پس از build و بدون نیاز به اجرای server جداگانه:

```text
npm run test:http
npx playwright install chromium
npm run test:browser
```

این دو دستور server تولیدی موقت با محدوده مصنوعی می‌سازند. نه suite مرورگر، انتخاب/بازیابی پروژه، انتشار، restart، دامنه، مسیر مرحله‌ای، تصمیم ساخت مقصد، تجربهٔ بصری دستیار، پوشهٔ بومی و حرکت رابط را می‌سنجند؛ عرض‌ها، کیبورد، متن۲۰۰٪ و axe طبق هر runner بررسی می‌شوند. `npm run test:studio` پنل و گزارش و `npm run test:interactions` انتخاب پوشهٔ واقعی بیرون workspace، فریم‌های حرکت، خروج دیالوگ، ارتفاع آکاردئون و کاهش حرکت را جدا بررسی می‌کنند. provider واقعی غیرفعال است؛ suite مسیر مرحله‌ای، transport مدل مصنوعی داخل process ایزوله و آزمون واقعی Node در workspace موقت دارد. هیچ API خارجی مصرف نمی‌شود. تصاویر و گزارش در `.artifacts/` محلی می‌مانند؛ این نتیجه شاهد اتصال حساب واقعی، deploy یا کیفیت عمومی مدل نیست.

برای دستیار واقعی، مسئول نصب `MODEL_API_KEY` و `MODEL_ID` را در `.env.local` تعیین و `LAUNCHLANE_ENABLE_LIVE_MODEL=true` کند؛ این کار اعتبار مدل مصرف می‌کند. اصلاح محلی جداگانه با `LAUNCHLANE_ENABLE_LOCAL_REPAIR=true` فعال می‌شود و هر محدوده پیش از اجرا تصمیم کاربر می‌خواهد. این worker فعلاً فقط آزمون مستقیم Node موجود را پشتیبانی می‌کند؛ shell یا نصب وابستگی ندارد. Node permissions محیط مجازی با شبکه جدا نیست. هر دو gate پیش‌فرض خاموش‌اند. بعد از تغییر تنظیمات server را restart کنید.

خواندن حساب واقعی با `LAUNCHLANE_ENABLE_LIVE_LIARA=true` و پیشنهاد/اجرای ساخت یا انتشار با `LAUNCHLANE_ENABLE_MUTATIONS=true` فعال می‌شوند. اتصال حساب، محدوده مجاز و بودجه باید مشخص باشند؛ فعال‌کردن این گزینه‌ها جای تصمیم سروری برای هر تغییر نیست. اگر صفحه می‌گوید «دستیار در این نصب خاموش است»، وضعیت مدلِ همین فرایند را بررسی و پس از تنظیم، server را restart کنید؛ نصب پیش‌فرض خودکار اعتبار مصرف نمی‌کند.

## استفاده از مسیر انتشار دستی

از تب «انتشار پروژه» وارد این مسیر شوید. گفت‌وگو در پنل اختیاری «دستیار هوشمند» پایین چپ است؛ تصمیم‌های آماده‌سازی و انتشار به نوشتن پیام نیاز ندارند.

1. وارد شوید و «انتخاب پوشه پروژه» یا «انتخاب از GitHub» را بزنید. «انتخاب پوشه از رایانه» پنجرهٔ بومی مرورگر را باز می‌کند؛ هر پوشهٔ برنامه را می‌توانید انتخاب کنید. پس از دیدن نام، تعداد و حجم فایل‌های مجاز، «بررسی این پروژه» کپی خصوصی را وارد میز کار می‌کند. فایل‌های خصوصی و وابستگی‌ها کنار گذاشته می‌شوند؛ اصل پوشه تغییر نمی‌کند و برای به‌روزرسانی باید دوباره وارد شود. ورود به تنظیم `LAUNCHLANE_WORKSPACE_ROOT` وابسته نیست؛ «انتخاب از پوشه‌های مجاز این نصب» مسیر فرعیِ مرور همان محدودهٔ سرور است. نمونه فقط با «امتحان با پروژه نمونه» انتخاب می‌شود. جزئیات و سقف‌ها در [ADR0016](docs/decisions/0016-browser-folder-import.md) آمده‌اند.
2. فایل‌ها خودکار و بدون اجرای script بررسی و بسته خصوصی آماده می‌شود. نام/حجم فایل‌ها قابل بازبینی است؛ مرحله دستی بسته‌سازی یا واردکردن دوباره پورت تشخیص‌داده‌شده ندارید. پروژه ناقص یا پورت نامعلوم سؤال مشخص ایجاد می‌کند.
3. از «حساب‌ها»، لیارا را متصل کنید. کلید به‌جای صرف ذخیره‌شدن، با سه GET محدود برای هویت، تیم ثابت و برنامه‌ها بررسی می‌شود. تیم مجاز را مسئول نصب در `LIARA_TEAM_ID` تعیین می‌کند؛ کاربر نام برنامه را از فهرست انتخاب می‌کند. allowlist مدیر، اگر تنظیم شده باشد، محدودیت بالادست است. اتصال فقط یک app انتخابی را مجاز می‌کند و مجوز تغییر همه برنامه‌ها نیست.
4. پیشنهاد شامل مقصد، نسخه اجرای Node، فایل‌های همان نسخه، اثر و وضعیت نامشخص هزینه است. تأیید به همین ورودی‌ها و revision GitHub متصل می‌شود؛ انتخاب تازه یا تغییر فایل‌ها تأیید قبلی را باطل می‌کند. انتشار تازه از پیشنهاد v5 استفاده می‌کند؛ v1/v2/v3/v4 برای اجرای تازه به پیشنهاد جدید نیاز دارند و نتیجه انتشار تاریخی v4 قابل بازخوانی است.
5. نتیجه با نوسازی و Back/Forward بازیابی و تازگی فایل‌ها بررسی می‌شود. بازیابی تأیید منقضی را تمدید نمی‌کند. ثبت تأیید، شروع انتشار و تأیید پاسخ سایت سه وضعیت جدا هستند.

برای ورود GitHub روی Windows x64، مسئول نصب یک‌بار `npm run setup:github` را اجرا کند. نسخه رسمی 2.103.0 با checksum بررسی و فقط در ابزارهای محلی نصب می‌شود؛ PATH یا ورود سراسری تغییر نمی‌کند. ورود از device flow ابزار رسمی و با grant انسان انجام می‌شود؛ credential باید در keyring باشد. مجوزهای گسترده CLI پیش از ورود توضیح داده می‌شوند؛ برای محصول عمومی GitHub App می‌تواند محدودتر باشد. [دلیل انتخاب روش](docs/decisions/0001-account-connections.md) و محدودیت‌ها ثبت شده‌اند.

برای «بررسی مشکل سایت»، برنامه متصل و نشانه مشکل را انتخاب کنید. نشانی عمومی امن سایت را می‌توان در حساب‌ها ثبت کرد؛ این کار دامنه لیارا را تغییر نمی‌دهد. پس از فعال‌شدن مجاز خواندن، اطلاعات همان برنامه و صفحه جمع‌آوری می‌شود؛ توضیح خودکار علت یک اقدام جدا و وابسته به آماده‌بودن مدل است. بررسی دوباره فقط پاسخ همان صفحه را می‌خواند و هیچ اصلاحی اجرا نمی‌کند. گزارش ابتدا مشکل، علت احتمالی، اقدام و نتیجه تازه را نشان می‌دهد؛ شواهد اولیه و تازه قابل بازکردن‌اند. داده ناکافی، علت قطعی تولید نمی‌کند.

«امتحان با نمونه اختلال» اختیاری و در تمام گزارش مشخص است؛ داده و تحلیل آن simulated/scripted هستند و هیچ تماس مدل/حساب ندارند. تغییر نامرتبط، 500 را حفظ می‌کند. نتیجه عادی و نمونه در SQLite متعلق به همان کاربر نگهداری و پس از جابه‌جایی، نوسازی یا ورود مجدد بازیابی می‌شوند؛ مرورگر فقط شناسه غیرحساس در URL دارد. تحلیل در حال اجرا با نوسازی تکرار نمی‌شود و پس از قطع فرایند، ناموفق و بدون بازپخش خودکار بازیابی می‌شود.

در نتیجه بررسی، «گزارش برای اصلاح کد» یک فایل Markdown برای برنامه‌نویس یا Coding Agent آماده می‌کند: روش تکرار همان صفحه، شواهد زمان‌دار، فرضیه‌های ارجاع‌دار، محدوده اصلاح و معیار بررسی. پیش‌نمایش و دریافت محلی‌اند؛ فایل به editor یا مدل دیگری ارسال نمی‌شود و مجوز تغییر نیست. کد پروژه، هویت حساب، details خام اضافی و credentialهای شناخته‌شده ضمیمه نمی‌شوند؛ اطلاعات خصوصی کسب‌وکار و الگوهای ناشناخته را پیش از اشتراک بازبینی کنید. آخرین مشاهده همان صفحه و نامعلوم‌ماندن پاسخ restart جدا ثبت می‌شوند. نام فایل/خط/دستور مخزن حدس زده نمی‌شود. داده مصنوعی با route/SQLite واقعی محلی و بازپخش آفلاین incident واقعی ذخیره‌شده 500→200 سنجیده شده‌اند؛ استفاده مستقل یک reader تازه هنوز تأیید نشده است.

`.env.example` با config مصرف‌شده هماهنگ است. هر سه gate `LAUNCHLANE_ENABLE_MUTATIONS`، `LAUNCHLANE_ENABLE_LIVE_MODEL` و `LAUNCHLANE_ENABLE_LIVE_LIARA` پیش‌فرض false هستند. فعال‌کردن mutation به‌تنهایی approval ایجاد نمی‌کند؛ انتشار به live-Liara، اتصال/app مجاز، origin و پیشنهاد v5 تازه نیاز دارد؛ راه‌اندازی دوباره از پیشنهاد مستقل v6 استفاده می‌کند. رمز پنل Liara توکن PaaS نیست؛ کلید مدل فقط به میزبان ثابت BoxAPI مجاز است. probe واقعی به نشانی HTTPS مجاز همان برنامه در حساب‌ها یا `LAUNCHLANE_PROBE_ORIGINS` نیاز دارد؛ تنظیم مدیر مقدم است، redirect و IP خصوصی رد می‌شوند. تا تطبیق حساب و مجوز scope/budget، این gateها خاموش بمانند.

انتشار Agent روی برنامه Node موجود و تازه‌ساخته‌شده با **WorkloadContract v7** آزموده شده است؛ معیار می‌تواند متن HTML/پاسخ عادی یا فیلد مشخص JSON باشد. شناسه داخلی برنامه، پلن، نسخه اصلی Node، همان بسته و معیار رفتار به تأیید متصل‌اند. مسیر دستی تاریخی v5 همچنان JSON/revision می‌خواهد؛ این الزام عمومی پروژه‌های Agent نیست. انتشار، پلن یا env را تغییر نمی‌دهد؛ هزینه پایه ساخت در پیشنهاد جدا از catalog معتبر می‌آید و هزینه نهایی نامعلوم می‌ماند. رسید بسته پیش از درخواست نسخه ذخیره می‌شود؛ پاسخ گم‌شده ارسال خودکار تازه ایجاد نمی‌کند. شواهد v4/v5 نیز حفظ شده‌اند و پذیرش عمومی همه runtimeها از این چرخه‌های محدود نتیجه نمی‌شود.

در «بررسی مشکل سایت»، راه‌اندازی دوباره یک اقدام اختیاری پس از مشاهده خطای تازه همان صفحه است. پیشنهاد، حساب و برنامه، نسخه فعلی، اثر وقفه و هزینه نامشخص را نشان می‌دهد. تأیید و اجرا جدا هستند؛ پس از پذیرش درخواست، پاسخ همان صفحه با همان نسخه دوباره خوانده می‌شود. این بررسی به پاسخ HTTP محدود است و پایان restart، رفع علت، محتوای صحیح یا بهبود سرعت را اثبات نمی‌کند. پاسخ گم‌شده، حتی با صفحه پاسخ‌گو، اجازه ارسال مجدد نمی‌دهد. نتیجه و شواهد پس از reload بازیابی می‌شوند؛ جزئیات محدودیت در [تصمیم restart](docs/decisions/0003-restart-acceptance.md) است. این مسیر با transport مصنوعی آزموده شده است؛ یک درخواست restart زنده پذیرفته شد، ولی همان صفحه 500 ماند؛ پایان restart و رفع علت تأیید نشده‌اند. جزئیات در docs/evidence/restart-live-cycle.md ثبت است.

با اعتبار، مدل و سقف مصرف مشخص، smoke صریح زیر حداکثر دو درخواست واقعی به BoxAPI می‌فرستد. این فرمان در checkها اجرا نمی‌شود و gate ذخیره‌شده را تغییر نمی‌دهد:

```text
npm run smoke:model -- --live
```

برای `gpt-6-luna` در مسیر Chat Completions، `MODEL_REASONING_EFFORT=none` برای ابزارخوانی لازم بود؛ بدون آن سرویس 400 داد. مدل‌های دیگر این نصب هنوز تست نشده‌اند. فهرست مدل‌های Chat مجاز در server enforce می‌شود؛ نه endpoint/provider پنهان داریم و نه fallback خودکار.

اگر build هنوز ادامه دارد، فقط نتیجه را دوباره بخوانید. پس از پاسخ ناموفق نیز «بررسی دوباره پاسخ و نسخه سایت» همان رسید را بدون انتشار دوباره بررسی می‌کند. READY، پاسخ liveness یا نسخه قبلی موفقیت محسوب نمی‌شود. توقف پیش از `release_started`، پس از بازخوانی، از release با رسید گم‌شده جدا می‌شود؛ پیشنهاد تازه همچنان تأیید تازه می‌خواهد. برای انتشار کد اصلاح‌شده، فایل‌ها را تغییر و پروژه را دوباره بررسی کنید.

## محدوده و دسترسی

MVP یک operator و یک scope مجاز دارد. privileged read/write به session، Host/Origin و در درخواست تغییر، CSRF وابسته‌اند؛ loopback جای authentication نیست. SQLite برای یک process است و approval/attempt به حافظه fallback نمی‌کنند. پاسخ گم‌شده یا قطع process، action را uncertain و write متعارض app را مسدود می‌کند.

بسته‌ها در `.data/source-artifacts/` یا زیر `LAUNCHLANE_STATE_DIR` خصوصی نگهداری می‌شوند؛ سقف هر بسته ۲۴ MiB، کل نگهداری ۱۲۸ MiB و ۳۲ فایل است. پاک‌سازی خودکار فعلاً وجود ندارد. حذف بسته متعلق به approval فعال، آن را قابل اجرا نمی‌کند؛ نگهداری/پاک‌سازی فقط پس از تعیین تکلیف اقدام‌ها انجام شود. پیشنهادهای قدیمی v1 خوانده می‌شوند ولی برای deploy به بسته متصل نیستند و باید دوباره ساخته شوند.

تشخیص فایل‌ها محدود و بدون اجرای کد است. در پروژه چندبخشی، پوشه همان برنامه را انتخاب کنید. نسخه Node از `engines.node` و `liara.json:node.version` انتخاب و در پیشنهاد نمایش داده می‌شود؛ تعارض، مقدار نامعتبر یا نبود شاخه سازگار، پیشنهاد اجرایی را می‌بندد. بدون تعیین نسخه، پیش‌فرض مستند 22 انتخاب می‌شود؛ نسخه Node رایانه مبنا نیست. انتخاب شاخه اصلی، نسخه جزئی محیط اجرا را تضمین نمی‌کند؛ این محدودیت کنار پیشنهاد دیده می‌شود. سناریوی زنده ثبت‌شده فقط Node 22 بود. حفظ دو متغیر پیش‌فرض در انتشار بعدی بررسی شد؛ حفظ secretها یا انواع دیگر تنظیمات از آن نتیجه نمی‌شود. مشاهده به صفحه اول حداکثر 50 release و JSON revision محدود است. rollback، reconcile حدسی رسید گم‌شده، چند process، میزبانی عمومی Launchlane و پایش دائمی پیاده نشده‌اند.

قابلیت پیاده‌نشده و بررسی زنده انجام‌نشده در گزارش وضعیت محصول صریح ثبت می‌شوند.


## آزمون worker ایزوله

مسیر هدایت‌شده اصلاح، Docker Linux engine و image دقیق زیر را لازم دارد؛ gate اصلاح همچنان پیش‌فرض خاموش است. دریافت image، اقدام مسئول نصب است و محصول خودکار pull یا اجرای host script نمی‌کند. container فقط workspace همان job را read-only می‌بیند و شبکه ندارد.

```powershell
docker pull node:22.23.3-bookworm-slim@sha256:3ed98443660ff48413b5af19ecefce3b9d50845a901a43420d47cc63a9fddbe9
npm run test:sandbox
```

این آزمون patch model مصنوعی و تست/containment واقعی Node22 دارد؛ بدون Docker یا image، fail می‌شود و skip را pass نمی‌نامد. generic npm install/build و فرم env هنوز پشتیبانی عمومی نیستند. [تصمیم worker](docs/decisions/0011-container-worker.md) حدود isolation و recovery را توضیح می‌دهد.
