# Agent استقرار و نگهداری Launchlane

## تصمیم جاری محصول: انتشار بدون چت

اطلاعات امنِ تأییدشده می‌توانند با تصمیم build همان پروژه در ساخت/تست/اجرای نسخه جدا استفاده شوند؛ فقط نام کلیدها روی کارت دیده می‌شود. تغییر configuration، رسید build قبلی را برای انتشار معتبر نگه نمی‌دارد. انتشار وابسته v10 می‌گیرد و configuration و workload جدا بررسی می‌شوند؛ «تنظیمات ذخیره شد» با «سایت سالم منتشر شد» یکی نیست. یک case واقعی Docker این اتصال را با مقدار مصنوعی سنجیده است؛ [حدود و تصمیم](decisions/0014-build-environment-binding.md).

تکمیل تازهٔ اطلاعات runtime در همین مسیر است: نیاز مستند به env، configure_env و فرم امن می‌آورد؛ مقدار در چت خواسته نمی‌شود. مرور نام کلیدها و احتمال restart، تصمیم مستقل می‌خواهد. refresh فقط reference/status را برمی‌گرداند و input رمز بازنمایی نمی‌شود؛ پس از configuration verified، دکمه ادامه همان run/بودجه را نگه می‌دارد. npm v3/Node22 دارای build/test/start موجود نیز با تصمیم container و oracle مستقل پیاده شده است؛ Next، env ساخت محلی و پذیرش زنده env هنوز از این شواهد قراردادی نتیجه نمی‌شوند.

ناوبری دقیقاً دو تب «انتشار پروژه» (پیش‌فرض، view=publish) و «بررسی مشکل سایت» (view=incident) دارد. view=agent قدیمی به انتشار نگاشت می‌شود و project معتبر حفظ می‌شود؛ navigation، بازکردن پنل و reload هیچ model/job/write تازه‌ای آغاز نمی‌کنند. چت فقط پنل اختیاری پایین چپ است. این بخش بر پیشنهادهای مکالمه‌محور تاریخی پایین مقدم است.

جریان اصلی: انتخاب محلی/GitHub → بررسی و آماده‌سازی → اطلاعات ضروری → تصمیم درباره مقصد/هزینه/تغییر → اجرا → بررسی همان صفحه. پس از انتخاب، pickerها کنار می‌روند و خلاصه قابل ویرایش می‌ماند. یک کارتِ قدم جاری، نتیجه و اقدام بعدی را نشان می‌دهد؛ جزئیات source/log/diff بازشدنی‌اند. کاربر goal یا فرمان فنی نمی‌نویسد. دکمه ورودی ساختاریافته سرور می‌سازد؛ مدل از نتایج واقعی ابزارهای همان registry ادامه می‌دهد.

نیاز به حساب، فرم اتصال دارد؛ اصلاح Node22 با scope/test صریح و container محدود انجام می‌شود؛ ساخت مقصد و انتشار به تصمیم‌های معتبر خودشان نیاز دارند. اصلاح، آزمون و انتخاب artifact در خود انتشار می‌مانند. بسته‌شدن چت و تغییر دو تب، مالکیت job یا بودجه را تغییر نمی‌دهند. سؤال چت فقط ابزار خواندن دارد و سابقه انتشار را جایگزین نمی‌کند.

پذیرش جاری محدود است: دو چرخه واقعی پروژه Node و اصلاح قبل از انتشار ثبت شده‌اند؛ نصب dependency، build عمومی Node/Next، فرم/اعمال امن env و چرخه تازه شکست انتشار→repair→redeploy هنوز پذیرفته نشده‌اند. نبود این‌ها با پیام دستی یا ظاهر مرحله‌نما کامل معرفی نمی‌شود. [گزارش و حدود](evidence/guided-publication.md).

## سوابق طرح و برش‌های قبلی

وضعیت: **مشخصات هدف با یک برش اجرایی اولیه؛ پذیرش کامل هسته هنوز انجام نشده است.** حلقه چندابزاری، تب مستقل پیش‌فرض و worker محدود اصلاح/آزمون Node پیاده شده‌اند. استقرار از خود گفت‌وگو، provision/env، معیار عمومی HTML و MCP هنوز آماده نیستند. وضعیت اجرا از TASKS.md و شواهد از [گزارش برش نخست](evidence/agent-first-slice.md) و verification.md خوانده می‌شود. کنترل‌ها و سابقه عملیات حفظ می‌شوند.

## هدف و تعریف موفقیت

کاربر هدف را می‌گوید و پروژه را معرفی می‌کند؛ Agent اطلاعات لازم را پیدا می‌کند، مسیر مناسب را انتخاب می‌کند، ابزارها را اجرا می‌کند، نتیجه را می‌خواند و تا رسیدن به نتیجه یا نیاز واقعی به تصمیم کاربر ادامه می‌دهد. نقش مدل به توضیح یک snapshot محدود نمی‌ماند.

سه مأموریت اصلی:

1. «این پروژه را منتشر کن»: شناخت source، آماده‌سازی، انتخاب منابع، پیشنهاد، تأیید، ایجاد/تنظیم مقصد، انتشار و بررسی برنامه.
2. «نسخه جدید را منتشر کن»: تشخیص تغییرات، اعتبارسنجی، پیشنهاد متناسب با همان پروژه، انتشار و مقایسه نتیجه.
3. «این صفحه خطا دارد یا کند شده»: تحقیق پویا، ارتباط با source، اصلاح کد/تنظیمات متناسب، تست، انتشار مجاز و بررسی همان رفتار.

برای بررسی یک app موجود، انتخاب همان برنامه کافی است؛ معرفی source پیش‌شرط خواندن وضعیت و logs نیست. اگر اصلاح کد لازم شد و ارتباط مخزن مشخص نبود، Agent همان‌وقت انتخاب source را می‌خواهد. برای هر مأموریت همه اطلاعات deployment را دوباره نپرسیم.

تجربه اصلی، **Agent داخل وب‌اپ** است. اتصال اجرایی Coding Agent برای اصلاح کد و MCP برای استفاده از ابزارهای مشترک، بخش‌های همین محصول‌اند. میز کار فعلی و APIهای آن مبنای توسعه هستند؛ محصول جداگانه و موتور مستقل دوم ساخته نمی‌شود.

## موجود، هدف و تقدم اجرا

| حوزه | پایه موجود در زمان تدوین | هدف توسعه |
| --- | --- | --- |
| source و حساب‌ها | بررسی ایستا، archive خصوصی، انتخاب محلی/GitHub و اتصال Liara | استفاده خودکار Agent از همان جریان، رفع ابهام واقعی و حفظ context |
| انتشار | مسیر محدود و تأییدشده برنامه Node موجود | انتخاب روش و پلن، ایجاد مقصد تازه، تنظیمات و انتشار از روی هدف |
| هوشمندی | ابزار خواندن snapshot و فرضیه تشخیصی محدود | انتخاب پویا میان ابزارهای پروژه، سرویس، مستند، اصلاح و verification |
| اصلاح کد | گزارش قابل دریافت؛ اصلاح در چرخه قبلی بیرون از مدل محصول انجام شد | مأموریت اجرایی Coding Agent، patch و تست برگشتی، انتشار و بررسی نتیجه |
| رابط | فرم‌ها و گزارش‌های عملیاتی موجود | مکالمه پروژه‌محور، کارت‌های اقدام و نتیجه، بدون اجبار به دانستن واژه فنی |
| نتیجه | معیار محدود JSON/revision و مقایسه symptom | قرارداد پاسخ HTML/API و مسیر کاربر، متناسب با خود پروژه |

هسته تحویل شامل Agent قابل استفاده در وب‌اپ، استقرار هدایت‌شده و چرخه اصلاح اجرایی است. پیش‌نمایش، برگشت، گسترش runtime، منابع وابسته، دامنه و MCP توسعه‌های برنامه‌دارند؛ هرکدام فقط پس از ساخت و آزمون، به‌عنوان capability موجود معرفی شوند. ترتیب وابستگی در TASKS.md است.

## جریان «پروژه را منتشر کن»

1. در برش تاریخی جایگزین‌شده، تب مستقل و پیش‌فرض «دستیار پروژه» یک ورودی «چه کاری برای پروژه‌تان انجام بدهم؟» و اقدام واضح انتخاب پوشه/GitHub دارد. تب‌های انتشار دستی و بررسی مشکل جدا هستند؛ فرم‌های فنی روی شروع گفت‌وگو انباشته نمی‌شوند. نمونه اختیاری است.
2. Agent از profile، manifest و تنظیمات موجود، root، runtime، build/start، port، env key names و نیازهای database/disk را استخراج می‌کند. ابهام چندپروژه‌ای با انتخاب پوشه حل می‌شود؛ اطلاعات قابل استخراج دوباره از کاربر پرسیده نمی‌شوند.
   مشاهده یک env name در کد به‌تنهایی اجباری‌بودن آن را ثابت نمی‌کند؛ default، validation و مسیر استفاده بررسی شوند تا فرم غیرضروری ساخته نشود.
3. حساب/تیم متصل، برنامه‌های موجود و catalog معتبر بررسی می‌شوند. Agent استفاده از برنامه موجود یا ساخت برنامه تازه و پلن متناسب را پیشنهاد می‌دهد؛ دلیل، گزینه جایگزین، هزینه و منبع/زمان آن قابل مشاهده‌اند.
4. فایل تنظیمات یا اصلاح کد لازم در workspace اصلاحِ جدا آماده و با فرمان‌های معتبر پروژه بررسی می‌شود. تغییرات هنوز source کاربر را بی‌خبر جایگزین نمی‌کنند.
5. یک کارت تصمیم، مقصد، مجموعه عملیات، تغییر source، منابع، هزینه و معیار بررسی را نشان می‌دهد. سؤال‌های ضروری یا ورودی محرمانه همان‌جا با کنترل مناسب دریافت می‌شوند.
6. پس از تأیید معتبر، اجرا مرحله‌ای و ثبت‌شده انجام می‌شود: ایجاد مقصد/منابعِ مندرج در پیشنهاد، تنظیمات، upload، release و مشاهده.
7. در شکست build/اجرا، Agent نتیجه را به ابزار تحقیق می‌دهد و راه اصلاح را انتخاب می‌کند. تغییر مؤثر source/هزینه/مقصد، پیشنهاد تازه می‌خواهد؛ read و تحلیل، تأیید تکراری ندارند.
8. نتیجه، لینک برنامه و موارد واقعاً بررسی‌شده را نشان می‌دهد. هدف عملیاتی محقق‌نشده با متن زیبا completed نمی‌شود.

## جریان «مشکل را اصلاح کن»

1. context پروژه، برنامه و نسخه قبلی حفظ می‌شود؛ کاربر مشکل را با زبان خودش می‌گوید.
2. Agent متناسب با فرضیه، ابزار بعدی را انتخاب می‌کند: logs، release، وضعیت، probe، metric معتبر، تنظیمات غیرمحرمانه یا فایل‌های مرتبط source.
3. اگر داده متناقض یا ناکافی است، بررسی هدفمند بعدی انجام می‌شود. تکرار بی‌فایده ابزار، پیشرفت حساب نمی‌شود.
4. برای مشکل کد، CodeRepairJob ساخته می‌شود. Coding Agent تغییر و آزمون می‌دهد؛ نتیجه از قرارداد اجرایی برمی‌گردد، نه صرفاً فایل راهنما.
5. خلاصه اصلاح، diff قابل بازبینی و نتیجه واقعی تست در کارت نمایش داده می‌شوند. تغییرات آماده‌شده به snapshot تازه متصل‌اند.
6. انتشار همان patch با مجوز معتبر انجام و همان صفحه/رفتار قبلی بررسی می‌شود. اصلاح نامرتبط و restart بی‌اثر به‌عنوان رفع مشکل معرفی نمی‌شوند.

## تصمیم‌ها، ابزارها و اجرای پایدار

مدل intent، ترتیب تحقیق و پیشنهاد را تعیین می‌کند. انتخاب هدف مجاز، اعتبار ابزار/آرگومان، قیمت‌گذاری عددی، مجوز و انتقال state در host enforce می‌شوند.

چرخه پیشنهادی:

    هدف و context → مدل → درخواست ابزار/سؤال/پیشنهاد
    → validation و policy → اجرا یا انتظار برای کاربر
    → نتیجه ابزار و رویداد پایدار → مدل → اقدام بعدی
    → سنجش معیار هدف → نتیجه نهایی

registry ابزارهای typed باید برای وب‌اپ و MCP مشترک باشد. نام‌های زیر **قرارداد داخلی پیشنهادی‌اند، نه endpoint موجود Liara**:

| خانواده ابزار | کار | مبنای پیاده‌سازی |
| --- | --- | --- |
| project/context | انتخاب، inspect، خواندن فایل مرتبط، profile و تغییرات نسخه | project-flows و workspace موجود |
| account/catalog | هویت، مقصد، catalog و هزینه معتبر | connection و read adapter؛ تکمیل catalog |
| proposal/approval | پیشنهاد واحد، دریافت تصمیم و بررسی scope | policy، ActionSpec و Store موجود |
| provision/configure | ساخت app، منابع وابسته و env | use case و journal جدید با قرارداد upstream تأییدشده |
| deploy/observe | آماده‌سازی artifact، انتشار و خواندن نتیجه | application/deployment، LiaraDeployClient و probe موجود |
| investigate/verify | خواندن هدفمند شواهد و بررسی رفتار | incident/runs، collector، latency و probe موجود |
| code repair | ساخت job، دریافت patch، تست و دریافت artifact | CodeRepair adapter جدید |
| documents/domain | راهنمای مرتبط و عملیات دامنه دارای مجوز | راهنمای موجود؛ adapterهای جدید هنگام پیاده‌سازی |

tool-result باید state، داده sanitized، محدودیت، receipt/evidence و اقدام قابل ادامه را جدا کند. متن ابزار یا خطای provider نباید به دستور system تبدیل شود. تشخیص قدیمی یک‌ابزاری می‌تواند سازگار بماند؛ محدودیت آن نباید روی runtime مأموریت‌های جدید تحمیل شود.

### مدل داده پیشنهادی

- AgentRun: مالک، پروژه/نسخه context، goal، plan revision، state، budget مصرف‌شده و نتیجه هدف.
- AgentMessage: نقش server-owned و بخش‌های typed؛ متن، کارت، سؤال، ارجاع شواهد یا نتیجه. replay پیام client مجوز tool call نیست.
- ToolInvocation: run/step/call ID، input digest، مرحله، زمان، خروجی sanitized و reference به action/job.
- DecisionPlan: مجموعه عملیات و آرگومان‌های مؤثر، source artifact، مقصد و selectors معتبر، اثر هزینه، preconditions و approvalهای مرتبط.
- CodeRepairJob: مأموریت، base revision/artifact، workspace اصلاح، patch receipt، فرمان و نتیجه تست و artifact خروجی.
- eventهای ترتیبی پایدار برای replay نمایشی؛ event اجرای تازه ایجاد نمی‌کند.

AgentRun/event و CodeRepairJob در برش نخست پیاده‌اند؛ plan چندمرحله‌ای و مدل‌های دیگر این بخش هنوز هدف توسعه‌اند. ابتدا نوع‌ها و جدول‌های موجود reuse شوند؛ فقط شکاف واقعی با migration جدید پوشش داده شود. action/approval/attempt فعلی مرجع write زیرساخت است؛ AgentRun مجوز موازی و ضعیف‌تر ایجاد نمی‌کند.

stateهای پیشنهادی run: queued، working، needs_input، needs_approval، paused، succeeded، partially_completed، failed، cancelled. هر انتقال با نتیجه واقعی مرتبط است. cancel انتظار، rollback عملیات پذیرفته‌شده remote نیست. پس از crash، قدم مبهم ابتدا reconcile می‌شود؛ مدل یا event replay آن را دوباره اجرا نمی‌کنند.

### تأیید مجموعه عملیات بدون کلیک‌های اضافی

کاربر می‌تواند یک مجموعه مشخص عملیات را در یک کارت تأیید کند؛ تأیید صفحه‌ای جدا برای هر read یا هر مرحله داخلی لازم نیست. هر write همچنان باید در server به همان actor، plan revision، args، اثر هزینه، scope و artifact تأییدشده متصل و مصرف‌شدنی باشد.

اگر app تازه ساخته می‌شود، پیشنهاد اولیه team و نام/نوع مقصد مورد تأیید را می‌بندد؛ ID برگشتی در receipt پایدار ثبت و همه مراحل بعد به همان ID متصل می‌شوند. ID از پاسخ نامطمئن یا app هم‌نام حدس زده نمی‌شود. تغییر مؤثر plan یا patch، رضایت تازه می‌خواهد. مرز «تأیید و ادامه» باید دقیقاً نشان دهد اجرا شروع می‌شود یا فقط تصمیم ثبت می‌شود؛ دو CTA هم‌معنا نسازیم.

## اتصال اجرایی Coding Agent

CodeRepair adapter یک قرارداد ثابت دارد: start، status، cancel و دریافت نتیجه. job باید goal، source snapshot، evidence، محدوده مجاز تغییر و acceptance داشته باشد؛ خروجی شامل base revision، diff، touched paths، فرمان/نتیجه تست، failures و artifact باشد.

در A06، runtime کدنویسی موجود و روش رسمی اجرای غیرتعاملی آن بررسی شود. اگر قابل استفاده بود، همان پشت adapter قرار بگیرد. اگر نبود، worker محدود patch/test با همان provider مجاز ساخته شود؛ خروجی دستی Markdown جای این قابلیت قبول نیست و نبود CLI مانع کل Agent نمی‌شود.

اصلاح روی شاخه/worktree یا کپی جدا و scoped انجام شود. فرمان build/test از پروژه و بررسی source معتبر انتخاب شود؛ فرمان دلخواه مدل اجرا نشود. تحلیل اولیه script اجرا نمی‌کند؛ اجرای تست و build در محدوده کاری مجاز، قابلیت صریح worker است. isolation روش واقعی و محدودیتش مستند شود؛ پوشه جدا به‌تنهایی sandbox امنیتی ادعا نشود.

worker به credential Liara/model غیرلازم، داده production و مسیرهای خارج job دسترسی نگیرد. تغییر package scripts، lockfile یا dependency باید در diff و review آشکار باشد. patch که base آن تغییر کرده یا آزمونش شکست خورده، خودکار deploy نشود. approval نهایی انتشار به artifact تازه متصل است. برای اجرای local work و برای انتشار remote، مرز رضایت روشن باشد؛ تست هر بار سؤال تکراری ایجاد نکند.

## قرارداد بررسی نتیجه

کاربر پروژه معمولی نباید مجبور شود endpoint مصنوعی JSON/revision اضافه کند. WorkloadContract آینده می‌تواند status و نشانه متنی/JSON صفحه، نسخه منتشرشده و در صورت نیاز یک مسیر مرورگری مشخص را ترکیب کند. oracle از هدف، source و رفتار پروژه استخراج یا در ابهام از کاربر روشن می‌شود.

قراردادهای v4/v5 تاریخی محفوظ می‌مانند. general verification با نسخه جدید spec و تست migration/compatibility افزوده شود. release آماده، HTTP 200، HTML درست و موفقیت مسیر کاربر، شواهد جدا هستند. نتیجه نهایی دقیقاً بگوید کدام مسیر بررسی شده است.

## UI و زبان؛ قرارداد طراحی

- یک جریان اصلی: context پروژه، کارت قدم جاری، فرم/تصمیم ضروری و نتیجه؛ چت اختیاری است. میز کار فعلی در بخش‌های مناسب reuse شود؛ داشبورد موازی و فرم‌محوری تازه نسازیم.
- شروع فقط با «پروژه‌تان را انتخاب کنید»؛ هدف انتشار با دکمه ثبت می‌شود. پس از انتخاب، پیشنهاد مرتبط نشان بده؛ انتخاب و نتیجه قبلی با cancel پاک نشوند.
- سؤال فقط برای تصمیم مؤثر یا داده غیرقابل استخراج. انتخاب پوشه/مخزن با picker، گزینه محدود با کنترل انتخاب، secret با فرم محرمانه؛ کاربر مجبور به تایپ پاسخ فنی در چت نشود.
- هزینه، مقصد، وقفه و اثر تغییر پیش از تأیید واضح‌اند. hash، provider مدل، run ID، schema و token counter در نمای عادی نیستند.
- متن محاوره‌ایِ محترمانه و دقیق؛ شناسه/خطای فنی در جزئیات قابل کپی. نمونه واژه‌ها در DESIGN.md است.
- progress از رویداد واقعی می‌آید. «فایل‌ها را بررسی می‌کنم»، «منتظر آماده‌شدن سایت هستم» و «این بخش نیاز به انتخاب شما دارد»؛ زنجیره فکر خصوصی مدل نمایش داده نمی‌شود.
- در stream، متن کاربر هنگام خواندن بالا به پایین نپرد؛ رفتن به آخر اختیاری و سؤال/تأیید تازه قابل پیدا کردن باشد. aria-live هر token را نخواند.
- موفقیت شامل لینک اصلی و نتیجه آزمون است؛ شکست شامل آنچه انجام شد، آنچه باقی است و یک قدم بعدی قابل اجرا.
- Eight states هر کنترل و اثرش روی داده مشخص باشد: idle، hover، focus، loading، empty، error، disabled و completed؛ لغو/انتظار تأیید/نتیجه نامعلوم نیز در سطح flow پوشش داده شوند.
- mobile، keyboard، RTL/LTR، متن ۲۰۰٪، focus و بازیابی پس از reload آزموده شوند. رنگ/فونت/فاصله از توکن‌های موجود؛ تغییر نام و هویت محصول لازم نیست.

## ارزیابی و پایان فاز

معیارهای افزوده AC17–AC34 در acceptance.md و وظایف A00–A19 در TASKS.md هستند. قبل از هر پیاده‌سازی، وضعیت واقعی شناسایی و دوباره‌کاری حذف شود. نتیجه live روی candidate ثبت شود؛ fixture برای قرارداد و failureها، مدل واقعی برای انتخاب ابزار/تحلیل و Liara واقعی برای عملیات سنجیده شوند.

دو مسیر پایان هسته: درخواست فارسی تازه → آماده‌سازی/پیشنهاد/تأیید → انتشار واقعی و بررسی برنامه؛ و درخواست تازه مشکل → تحقیق → CodeRepair واقعی → تست → انتشار تأییدشده → بررسی همان رفتار. برای هر دو، حالت ابهام، تصمیم ردشده، failure و ادامه پس از قطع نیز بررسی شوند.

دستورات جدید، config و capability تنها پس از پیاده‌سازی به اسناد اجرای محصول اضافه شوند. این سند وعده اجرای انجام‌نشده یا تغییر خودکار gate نصب نیست.
